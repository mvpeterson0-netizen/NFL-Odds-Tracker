# Stix tweet plan: how scheduled tasks use the admin "Tweet plan" tab (Michael, 2026-11-11; drafts + instant saves added 2026-11-13)

Michael edits the weekly @StixNFL tweet plan on the Stix admin page (sharpstix.com, `#/admin` > Tweet plan tab) and presses **Submit changes**. Since 016 (2026-11-13) edits are **saved immediately**; Michael opens a tweet on that tab to see Claude's saved draft (text + images), copies it, posts on X himself and taps **Mark posted**. The plan lives in Supabase (`supabase/015_tweet_plan.sql` and `supabase/016_tweet_drafts.sql`: tables `tweet_plan`, `tweet_requests`, `tweet_drafts`). This doc is how every scheduled tweet task and the daily roll task read and update it. If this doc conflicts with a topic, time or instruction in a task prompt, **the plan row wins** for: what the tweet is about, extra direction, and the planned post date/time. Everything in the playbook's hard rules, gates, honesty rules and the LENGTH RULE in `claude/tweet-posting.md` still wins over the row (a direction can never make you invent a number, skip a gate, or post a negative image next to a positive text).

## Functions (all POST; all need `p_token`)
- `tweet_agent_pending {p_token}` -> `{requests: [{id, created_at, changes: [{op, slot_key, fields}]}], plan: [rows]}`. Since 016, pending requests exist only for changes to a tweet that is already scheduled on X (the plan itself is already updated). `op` is `update` (or missing = update), `add` or `delete`. Rows have: `slot_key` (`YYYY-MM-DD_<slot>`, SU1 slots are `SU1a`..`SU1d`; tweets Michael adds on the page have keys like `c1k3x9ab`), `slot`, `topic` ("Tweet about"), `direction` (notes for Claude), `post_date`, `post_time` (Central, `HH:MM:SS`), `status`, `x_time`, `last_result`, `data_ready`, `draft_run`.
- `tweet_agent_update_plan {p_token, p_slot_key, p_fields}`: fields allowed: topic, direction, post_date, post_time, status, x_time, last_result, data_ready, draft_run (all text; empty string clears date/time/direction).
- `tweet_agent_add_row {p_token, p_row}`: adds a row only if its slot_key doesn't exist (`slot_key, slot, topic, day_label, post_date, post_time, sort_order, data_ready, draft_run, direction`).
- `tweet_agent_delete_row {p_token, p_slot_key}`: removes a row (only after any X item for it is cancelled).
- `tweet_agent_finish {p_token, p_id, p_status, p_result}`: p_status `done` or `needs_attention`.
- `tweet_agent_save_draft {p_token, p_slot_key, p_body, p_images}`: see section D.

## A. Every tweet task, before drafting
1. Call `tweet_agent_pending`. Find your slot's row: `slot_key = <the Central date you will post on>_<slot>` (e.g. `2026-11-14_S1`). Use the first row for that slot with `post_date` on or after today if the exact key is missing; if there is no row, add one with the defaults from the prompt/playbook (`tweet_agent_add_row`) and go on. A row that has a pending `delete` request counts as deleted: do not draft it.
2. Status `Failed / skipped` or `Manual`: do not draft or schedule. Log one line to `claude/tweet-drafts-log.md`, say in chat "<slot> skipped per tweet plan", stop. Status `Posted`: already posted; do not draft it again.
3. Otherwise use the row: **topic** = what the tweet is about (if it differs from the default, follow it as long as the data for it really exists and the playbook rules allow; if not, draft the default and explain why); **direction** = extra instruction from Michael, followed as far as the hard rules allow (say in the hand-off which parts you followed or couldn't); **post_date + post_time** = the planned post time (replaces the time in the task prompt and in `tweet-posting.md` step 1; still apply the "at least 6 minutes ahead" rule, and never schedule after the relevant kickoff). A blank date/time = use the prompt's time.
4. For SU1 (four tweets) read rows `SU1a`..`SU1d` separately: each row has its own topic, direction and time.

## B. Every tweet task, after drafting and after scheduling
Update the row with `tweet_agent_update_plan`: after drafting and saving the draft (section D) `status: "Drafted (chat only)"` (the label is historical: it means the draft is saved in the app and in chat, not on X), `draft_run: "<day> <time> CT"`, `last_result: "<one line>"`; if you also scheduled on X `status: "Scheduled on X"`, `x_time: "<day date time> CT"`; if scheduling on X failed or the Chrome tools were not available, leave the status as Drafted and put `last_result: "<one line>; not scheduled on X: <reason>"` (this is expected in cloud runs, not a failure). Never set `Posted`: only Michael does, with Mark posted. Also update the Sheet tracker if you can (`claude/tweet-posting.md`, Live tracker); the Supabase row is the source of truth.

## C. Daily roll task (scheduled once a day, about 5:40 AM CT; cloud is fine)
1. `tweet_agent_pending`. Make sure plan rows exist for today and the next 7 days (Central dates) using the weekly calendar in `claude/tweet-schedule.md` and the exceptions list in the playbook (`tweet_agent_add_row`; defaults: topic from the calendar, post time from the playbook table; add only, never overwrite or delete a row; skip event-driven rows such as ARB). Past rows stay as history; the app hides them under "Show earlier". For holiday or non-standard weeks add the rows you can and list the rest for Michael.
2. Pending requests (only changes to tweets already scheduled on X): the X scheduler can only be changed by Claude in Chrome on Michael's computer. If the Chrome tools exist in this session, follow `claude/tweet-posting.md` to delete the scheduled item and reschedule/recompose (never post now; verify in the scheduled list), then set `x_time` and finish the request `done`. If they don't, finish the request `needs_attention` with "Plan updated; X still has the old schedule (<old time>) because the Chrome tools aren't available in this run. Open Claude on your computer and say 'apply the tweet plan changes'." For a `delete` of a row that is scheduled on X: cancel it via Chrome (Scheduled list > Edit > select > Delete, verify) and then call `tweet_agent_delete_row`; without Chrome finish `needs_attention` ("X still has this tweet scheduled for <time>; open Claude on your computer and say 'apply the tweet plan changes'"). A row with status `Posted`: never delete; never touch.
3. A tweet Michael added on the page (`add`, key like `c1k3x9ab`) is already in the plan. No scheduled task drafts custom tweets: when Michael asks ("draft <topic>"), draft it like any slot (sections A, B, D, playbook rules and gates). Note: if a recurring task for a deleted default slot runs later, it recreates the row by section A; to skip a default slot, set its status to `Failed / skipped` instead of deleting. Tell Michael this once.
4. Send `SendUserMessage` once only if something needs Michael (non-standard week rows, requests needing attention); otherwise stay silent. Never post or schedule anything on X from this task.

## D. Save the draft in the app (added 2026-11-13)
After a tweet passes its gates, save its final text and image(s) so Michael can copy them from the Tweet plan tab (open the tweet). One call per slot_key, same connection/headers/token as above:
- `tweet_agent_save_draft {p_token, p_slot_key, p_body, p_images}`: `p_body` = the exact tweet text (max 4000 chars; the tweet itself is still max 280); `p_images` = array of up to 4 `{"name": "<slot>_1.png", "mime": "image/png" or "image/jpeg", "data": "<base64, no prefix>"}`. Each image's base64 must stay under about 2 MB (~1.5 MB of file): if a screenshot is bigger, downscale to max 1170 px wide and save as optimized PNG or JPEG quality 85 with PIL first. Saving again for the same slot replaces the earlier draft.
- Save only the final text and the same image(s) delivered to chat; never save a gate-failed draft. If the call fails, say so in the hand-off and keep delivering to chat as usual.
- Michael posts on X himself and taps **Mark posted** (the row becomes Posted). Tasks never set Posted.
- Plan edits from the Tweet plan tab save immediately (since 016). A pending request exists only for a change to a tweet that is already scheduled on X.
